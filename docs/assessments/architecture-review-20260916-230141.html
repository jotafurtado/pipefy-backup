1. Travessia de cards duplicada no PipefyService

Strong

Files: app/Services/PipefyService.php (métodos getCards e eachCardPage)

Problem

O mesmo documento GraphQL (~45 linhas) e o mesmo loop de paginação existem duas vezes, verbatim. getCards ainda ganhou um callback $onPageFetched aparafusado — um parâmetro que existe só para imitar o outro método. O módulo é shallow: duas interfaces para um único comportamento. Pior: a superfície de teste (getCards, coberta por 4 property tests) não é a seam de produção (eachCardPage, usada pelo BackupPipeJob). Uma mudança de campo na API exige o mesmo edit em dois lugares, e nada garante que ambos mudem juntos.

Solution

Uma única travessia paginada atrás da seam (ex.: gerador privado paginateCards rendendo páginas). eachCardPage vira a interface pública enxuta; getCards vira um adapter fino que acumula — ou deixa de existir, com os tests migrados para a seam real. Deletion test: deletar o corpo de um dos loops hoje não concentra complexidade — ela reaparece idêntica no outro. Sinal clássico de módulo shallow.

getCards(pipeId, ?onPageFetched) · eachCardPage(pipeId, onPage) + GraphQL ×2
2 loops de paginação + 2 queries idênticas — interface quase tão complexa quanto a implementação
eachCardPage(pipeId, onPage): int
1 travessia + 1 query; getCards vira adapter fino (ou some)
Benefits. Locality: mudança de campo da API num só lugar. Leverage: uma implementação serve produção e tests. Tests passam a atravessar a mesma seam que a produção — "the interface is the test surface".

2. Layout de arquivos do backup espalhado em 4 módulos

Strong

Files: app/Jobs/BackupPipeJob.php · app/Jobs/BackupCardJob.php · app/Jobs/VerifyCardBackupJob.php · app/Console/Commands/PipefyVerifyBackupCommand.php

Problem

Os caminhos pipefy-backup/{pipe}/cards/{card}.json, …/attachments/{card}/{file} e …/cards/index.json são interpolados à mão em 4 módulos. O fallback de filename (basename($path) ?: 'unknown') está copiado em 3 lugares (PipefyService::getCardAttachments, BackupCardJob::downloadAttachment, VerifyCardBackupJob::handle). Zero locality: renomear o layout quebra N callers em silêncio, e writer e reader podem divergir sem que nenhum teste acuse.

Solution

Um módulo de layout (ex.: BackupPaths) com interface pequena: cardJson(pipeId, cardId), attachment(pipeId, cardId, filename), index(pipeId), filename(attachment). Writers e readers passam pela mesma seam; o conhecimento do layout vive num lugar só. One adapter = hypothetical seam não se aplica aqui — já há 4 adapters reais divergindo.

4 módulos interpolando strings + basename ×3
conhecimento do layout replicado em cada caller
BackupPaths: cardJson · attachment · index · filename
layout + fallbacks num módulo só; callers só conhecem a interface
Benefits. Locality: fix once, fixed everywhere — writer e reader nunca mais divergem. Leverage: tests de round-trip (já existe PipefyBackupCardsJsonRoundTripPropertyTest) atravessam a interface real do layout.

3. Lógica de retry duplicada entre console e HTTP

Worth exploring

Files: app/Console/Commands/PipefyBackupAllCommand.php::handleRetry · app/Http/Controllers/BackupStatusController.php::retry

Problem

Resetar um card falho (status, error_message, errors_count, started_at, completed_at) + redespachar BackupCardJob está escrito duas vezes, uma por seam de entrada (console, HTTP). As listas de campos já diferem em detalhe e vão divergir mais. Conhecimento de "o que significa retentar" mora nos callers, não atrás de uma seam.

Solution

Um módulo de retry com interface única (ex.: retryFailed(batchId): RetryReport); comando e controller viram adapters finos de apresentação. O reset de campos e o dispatch vivem atrás da seam.

handleRetry() × retry() — reset + dispatch em cada caller
listas de campos duplicadas, divergindo
retryFailed(batchId): RetryReport
reset + dispatch + relatório num módulo; console/HTTP só apresentam
Benefits. Locality: regra de retry muda num lugar (os tests Retry* já cobrem o comportamento — atravessariam a seam única). Leverage: terceira entrada futura (ex.: schedule) reusa sem copiar.

4. Agregação de conclusão do batch dentro do job de card

Worth exploring

Files: app/Jobs/BackupCardJob.php::aggregatePipeBackupStatus · generateIndexJson

Problem

Todo BackupCardJob que termina roda ~5 queries de contagem para descobrir se é "o último" e, se for, fecha o batch e gera o index.json. Responsabilidade de nível-batch mora num módulo de nível-card — sem locality (a regra "quando o backup termina" só se entende lendo o job de card) e com condição de corrida implícita entre workers (last-writer-wins sem lock).

Solution

Mover "tentar concluir o batch" para trás de uma seam própria (ex.: PipeBackup::tryComplete() no model ou módulo dedicado), com a geração do index.json junto. O job de card volta a ter uma interface honesta: processar um card.

BackupCardJob.handle + aggregate + generateIndex
card, batch e índice misturados; N queries por card
handle(card) · tryComplete(): bool
conclusão e índice atrás da seam do batch
Benefits. Locality: a regra de conclusão é testável sem despachar jobs (tests BackupPipeJobStatusTransition* e PipeBackupStatusDerivation* atravessariam a seam). Abre caminho para fechar o batch com lock, sem tocar no job de card.

5. Job de verificação usado como função via `new` + `handle()`

Worth exploring

Files: app/Console/Commands/PipefyVerifyBackupCommand.php::verifyPipe · app/Jobs/VerifyCardBackupJob.php

Problem

O comando instancia o job na mão (new VerifyCardBackupJob(...)) e chama handle() direto — usa a classe de queue como função. A interface que o caller precisa conhecer (ordem dos construtores, shape array{ok, issues}) é a interface de um adapter de fila, não a de um módulo de verificação. Se o job ganhar fila de verdade, o comando quebra junto.

Solution

Extrair a verificação para um módulo com interface pequena (ex.: verifyCardBackup(pipeId, cardId, title): VerificationResult); o job e o comando viram dois adapters sobre a mesma seam. Two adapters = real seam — ela já existe de fato, só não está declarada.

new VerifyCardBackupJob(pipe, card, title) → handle(): array
caller conhece o adapter de fila
verifyCardBackup(...): VerificationResult
job e comando como adapters da mesma seam
Benefits. Locality: regra de integridade num lugar, testável sem construir job (tests VerifyCardBackup* já existem e migrariam para a seam). Leverage: verificação reutilizável pós-backup automático.

Top recommendation

Candidato 1 (travessia de cards) primeiro: é o deepening mais barato (um método privado + um adapter fino), elimina a duplicação verbatim mais perigosa (query GraphQL ×2) e — o principal — alinha a superfície de teste com a seam de produção, que hoje estão em métodos diferentes. Em seguida o 2 (layout), que dá locality a todos os readers/writers e protege o par writer↔verifier.
